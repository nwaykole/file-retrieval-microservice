Customer file retrieval service

A simple, production-shaped design: a load balancer in front, stateless pods spread over three zones, a database for file details and a bucket for the files themselves. Extras are listed as future improvements.

Request path

  1. The customer calls GET /v1/files/{id}/content over HTTPS with the session cookie from POST /auth/login (username and password; no JWT).
  2. The load balancer picks a healthy pod in any zone.
  3. The pod hashes the cookie and looks up the session in Cloud SQL. A missing, expired or logged-out session gets 401; a valid one gives the customer id.
  4. It asks Cloud SQL for that file, filtered by that customer id. Someone else's file returns 404.
  5. Small files (up to 1 MiB) are read from the bucket and returned directly.
  6. Large files get a link that works for 5 minutes, and the customer downloads straight from Cloud Storage.

Future improvements (not in v1)

  • Log in through an external identity provider (OIDC/JWT); Cloud Armor and login rate limits.
  • Pub/Sub plus worker pods to virus-scan new uploads in the background.
  • Redis cache or a database read replica if the database becomes the bottleneck.
  • A second region for disaster recovery and a 99.99% target.
  • VPC Service Controls around the bucket and database to stop data leaving.
  • Image signing with Binary Authorization; canary releases with automatic rollback.
  • Distributed tracing and dashboards as code.

What each piece does

Load balancerOne public HTTPS address; sends each request to a healthy pod.
GKE AutopilotRuns the containers across three zones; Google looks after the servers.
file-service podsThe app: checks who you are, finds your file, returns it or a link to it.
Cloud SQLAccounts, login sessions, file details and ownership; survives a zone failure.
Cloud StorageStores the files cheaply and durably; serves large downloads itself.
MonitoringTracks the success-rate and latency targets and alerts when they slip.
